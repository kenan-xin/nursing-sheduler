- The base pin `d63519b` is NOT on v1 `dev`. It is on `feature/genie`: `git branch --contains d63519b` lists only `feature/genie`. The merge base with `dev` is `89190ab` (2026-07-20). This matters for every sync lane, because `git diff d63519b dev` also reverts the 17 genie-only commits.

The genie commit `64c84a3` (kenan.xin, 2026-07-15, "feat: add shift working time and remove sentry") deleted them. - The lane contains ops features for an internet-facing backend. They are bearer auth, a body-size guard, a solver allowlist, a self-claimed benchmark score, Sentry error and abuse reports, and weekly usage telemetry sent by Mailgun.
- v2 has no equivalent for any of them. The v2 backend is private: the `backend` service in `docker/compose.yml` has no `ports:`, "reached exclusively via the web BFF (DL11 D1)". The BFF (`web/lib/bff`) does no auth, no rate limit and no telemetry. It forwards only the client-id cookie and rewrites its `Secure` flag.
- Risk 1: `sentry.py:40` hardcodes `DEFAULT_SENTRY_DSN`, which is the upstream author's Sentry project. It also sets `send_default_pii=True` (`sentry.py:63`) and attaches YAML (`sentry.py:192`). If you adopt the file verbatim and do not set `DISABLE_SENTRY`, v2 errors go to a third-party Sentry project.
- Risk 2: v1 adds the keys `auth` and `claimed_performance` to `/info`. The BFF parser needs an exact key set (`web/app/api/info/validate.ts:27,41`). Until the parser changes, `/api/info` returns 502 `invalid_upstream_response`.
- Risk 3: suspicion counting is per client address. Behind the BFF, every request comes from the BFF container. The BFF does not forward `X-Forwarded-For` (`web/lib/bff/upstream.ts:18`), so all users share one address.

## 4. Open decisions for the user

- D1: turn on backend bearer auth in v2? Recommendation: not now. The v2 backend is private behind the BFF (DL11 D1), so auth adds a secret to manage but no protection. Adopt the module for parity and leave `API_AUTH_REQUIRED` unset. If you later expose the backend or the diagnostic contract, add a server-only `BACKEND_API_TOKEN` to the BFF. The BFF then sets `Authorization` on every upstream call. The fetch-stream events call can carry that header too, so the stream token is not needed.
- D2: accept a configurable solver allowlist? In code, this reverses the U31 "CP-SAT only" boundary. The behavior stays the same. Recommendation: yes, with the default allowlist `ortools/cp-sat` and no PuLP dependency. This keeps `config.py` and `solver_options.py` verbatim. The browser still sends no solver field.
- D3: bring Sentry back to v2? Recommendation: yes, but as opt-in. Patch `DEFAULT_SENTRY_DSN` to `None`, so that no event leaves unless you set `SENTRY_DSN` to your own project. Review `send_default_pii=True` against `PRIVACY.md`. Never report to the upstream DSN.
- D4: suspicion reports behind the BFF. Recommendation: if D3 is yes, set `SUSPICION_COUNTER_ENABLED=false` in v2 compose. Keep it off until the BFF forwards a trusted client address: an `X-Forwarded-For` that the BFF sets, and uvicorn that trusts only the `web` service.
- D5: weekly usage telemetry and Mailgun email? Recommendation: adopt the code with `USAGE_METRICS_ENABLED=false` and no `usage-reporter` service. Turn it on only after a privacy review, because it keeps the client-id cookie and the schedule shape for 30 days. Exclude `assistant_diagnostic` jobs.
- D6 (process): the sync base. Recommendation: diff v1 against the merge base `89190ab`, not against `d63519b`. Record `d63519b` as the v2 content pin and `89190ab` as its v1 `dev` ancestor in the T19 manifest. The genie-only commits (for example `64c84a3`) are v2 decisions, not v1 changes to revert.
